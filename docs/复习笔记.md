## 一、A2A 协议是什么

**A2A（Agent2Agent）** 是 Google 2025 年发起的开放协议，解决的是 **Agent 与 Agent 之间**
如何互相发现、通信、委派任务的问题。核心概念：

| 概念 | 说明 | 本项目对应 |
|------|------|-----------|
| **Agent Card** | Agent 的"名片"，JSON 描述能力/技能/地址，暴露在 `/.well-known/agent.json` | `weather_agent.py` 里的 `AgentCard(name, url, skills=...)` |
| **Skill** | Agent 声明自己会做什么（名称+描述+示例） | `AgentSkill(name="query_weather", examples=[...])` |
| **Task** | 一次任务请求的载体，含 id / sessionId / message / status / artifacts | 客户端构造 `Task(message=...)` 发给服务端 |
| **TaskState** | 任务状态机：submitted → working → completed / failed / **input-required** | `input-required` 用于向用户追问缺失信息 |
| **Artifact** | 任务产出物（文本/文件/结构化数据），完成态的正式结果放这里 | `task.artifacts = [{"parts": [{"type":"text","text": ...}]}]` |

通信方式：HTTP + JSON-RPC。本项目用的社区包 `python-a2a`，其服务端路由是
`POST /tasks/send`，`params` 就是完整的 Task 字典；响应的 `result` 是处理后的 Task。

**关键实现细节（这次踩过的坑）**：`python_a2a` 的 `A2AServer.handle_task(task)` 是
**同步调用、要求返回 Task 对象**（不是 TaskStatus，也不能是 async def——否则返回
coroutine 直接序列化失败）。文本结果的约定：完成态放 `artifacts`，追问/失败放
`status.message`。

## 二、A2A 与 MCP 的区别与配合

一句话：**MCP 管"Agent 用工具"，A2A 管"Agent 找同伴"**。

| 维度 | MCP (Model Context Protocol) | A2A (Agent2Agent) |
|------|------------------------------|-------------------|
| 发起方 | Anthropic (2024) | Google (2025) |
| 解决问题 | LLM/Agent 如何标准化调用**工具和数据源** | Agent 之间如何**互相发现与协作** |
| 抽象层级 | 垂直：Agent ↔ 资源（数据库、API、文件） | 水平：Agent ↔ Agent（对等协作） |
| 核心原语 | Tool / Resource / Prompt | Agent Card / Task / Skill / Artifact |
| 通信 | JSON-RPC（stdio / streamable-http / SSE） | HTTP + JSON-RPC（Task 语义） |
| 类比 | "给 Agent 插 USB 外设" | "给 Agent 拉工作群" |

**本项目的配合方式**（两层协议各司其职）：

```
编排层(main/app) --A2A--> 天气/票务/订票 Agent --MCP--> 天气/票务/订单 MCP --SQL--> DB
                              │
订票 Agent ------A2A（横向协作）------> 票务 Agent
```

- Agent 对外是 A2A 服务端（被编排层调用），对内是 MCP 客户端（调数据服务）。
- 订票 Agent 同时还是 A2A 客户端——查余票时直接 A2A 调票务 Agent，这是
  "Agent 委派 Agent"的典型样例。

## 三、多 Agent 通信模式：编排式 vs 协作式

**1. 编排式（Orchestration，中心化）**
一个编排者（本项目是 `src/main.py` / `src/app.py` 的意图识别层）负责：
意图识别 → 任务拆分/改写 → 路由到专职 Agent → 汇总/总结结果。

- 优点：全局可控、易调试、对话历史统一管理、结果可统一润色
- 缺点：编排者是单点，所有流量都过它；Agent 间无自主性

**2. 协作式（Peer-to-peer / Choreography，去中心化）**
Agent 之间直接对话委派，无需回到中心。本项目样例：订票 Agent 缺少票务信息时，
**直接 A2A 调用票务 Agent** 查余票，拿到票务 ID 再走订单 MCP 下单。

- 优点：链路短、职责内聚（订票的完整闭环由订票 Agent 自己负责）
- 缺点：调用拓扑复杂后难追踪，容易出现循环调用/级联失败

**本项目 = 混合模式**：顶层编排式（用户入口统一），底层局部协作式（order→ticket）。
这也是工业界常见形态：编排层管"意图与会话"，Agent 层管"领域闭环"。

**每个 Agent 的职责**：

| Agent | 端口 | 职责 | 下游 |
|-------|------|------|------|
| WeatherQueryAgent | 5005 | 天气自然语言查询，LLM Text2SQL | Weather MCP :8000 |
| TicketQueryAgent | 5006 | 火车/机票/演唱会余票查询，LLM Text2SQL | Ticket MCP :8001 |
| OrderBookingAgent | 5007 | 意图解析→查余票（A2A 调票务Agent）→下单/扣库存 | Ticket Agent :5006 + Order MCP :8002 |

## 四、Function Calling 原理

LLM 本身只会生成文本，Function Calling（工具调用）是让它"能做事"的机制：

1. **声明**：把工具的名称/用途/参数 JSON Schema 随对话发给模型
2. **决策**：模型判断是否需要调用工具，输出结构化的调用意图
   `{"name": "query_weather", "arguments": {"city": "北京"}}`（本质仍是"生成文本"，
   只是被约束成 JSON，且经过了函数调用样本的微调）
3. **执行**：**由应用侧执行**真正的函数——模型永远不亲自执行
4. **回填**：把函数返回值作为 `tool` 角色消息喂回模型，模型据此生成最终回答

要点：
- 模型可能产生**幻觉参数**（编造不存在的枚举值），所以应用侧必须校验参数
- MCP 可以理解为 Function Calling 的**标准化外置**：工具定义、发现、调用协议
  都统一了，任何 MCP 客户端可复用任何 MCP 服务器的工具
- 本项目一处细节：`FastMCP` 的 `@mcp.tool()` 装饰器自动从函数签名+docstring
  生成工具 Schema，这就是"声明"步骤的自动化

本项目实际上用了**两种"让 LLM 做事"的路子**：
- Prompt 约束输出 JSON/SQL（意图识别、Text2SQL）——手工解析，灵活但要防格式漂移
- MCP 工具调用（Agent → MCP 服务）——协议化，强类型

## 五、Text2SQL 的安全防线（重点）

LLM 生成的 SQL 是**不可信输入**——用户一句"查北京天气；顺便 DROP TABLE orders"
可能被模型忠实翻译。**Prompt 里写"只允许 SELECT"不是安全边界**，模型可被注入
（prompt injection）或产生幻觉。标准防线（纵深防御）：

1. **参数化查询（首选）**：凡是结构化入参（城市/日期/ID），一律占位符绑定，
   杜绝字符串拼接。本项目 `query_train_tickets` 等结构化工具全部参数化。
2. **只允许 SELECT + 单语句**：语法层校验（本项目用 sqlparse 判断
   `get_type() == 'SELECT'`），并拒绝分号多语句、注释（`--`、`/*`、`#`）。
3. **关键字黑名单（正则兜底）**：INSERT/UPDATE/DELETE/DROP/ALTER/UNION/
   SLEEP/BENCHMARK/INTO OUTFILE/information_schema 等，词边界匹配。
4. **表名白名单**：每个服务只能查自己的表（天气 MCP 只能查 `weather_data`），
   子查询里的表也要检查——本项目对 FROM/JOIN 逐个提取比对。
5. **强制 LIMIT**：无 LIMIT 自动追加、超上限强制收紧，防大结果集拖库。
6. **只读数据库账号（生产必备）**：给 Text2SQL 链路单独建 `GRANT SELECT ON
   travel_rag.weather_data TO 'ro_user'` 的账号，数据库层兜底——即使前面全被
   绕过，写操作也会被权限拒绝。本项目 demo 用 SQLite 未做账号隔离，生产必须做。
7. 其他：查询超时、行数/字节数上限、审计日志（本项目在拦截时 `logger.warning`）。

本项目实现：`src/mcp_servers/sql_guard.py` 的 `validate_select(sql, allowed_tables)`，
覆盖 2~5；`base_service.execute_select` 是 LLM SQL 的**唯一入口**，内部参数化查询
走 `execute_query(sql, params)`。单测见 `tests/test_sql_guard.py`（17 个用例）。

## 七、这次修了什么 bug（教训）

**1. 调用不存在的方法（AttributeError 系列）——从未跑通的铁证**
- 现象：`weather_agent` / `order_agent` 全程调用 `create_success_response` /
  `create_error_response` / `create_input_required_response` / `get_current_date()`，
  而 `base_agent` 里只有 `success_response` / `current_date`（属性）。任何一次请求
  进来就 AttributeError。
- 修法：在 `BaseAgent` 统一实现 `create_*_response` 三件套（返回轻量 `AgentReply`），
  三个 Agent 统一改用同一套名字；日期统一用 `current_date` 属性。
- 教训：**基类与子类由"两次不同的生成/编写"产生而从未联调**。写完必须至少跑一次
  端到端；接口命名要有单一事实来源。

**2. 框架契约理解错误（比 bug 1 更隐蔽）**
- 现象：Agent 实现的是 `async def handle_task -> TaskStatus`，但 `python_a2a`
  服务端**同步调用** `handle_task` 且要求**返回 Task**。即使修好 bug 1，返回的
  coroutine 也无法序列化，客户端解析也全错（`result.state` 实际在
  `result.status.state`）。原 `TicketAgentClient` 手搓 JSON-RPC 打 `/a2a` 端点，
  实测直接 500。
- 修法：`BaseAgent.handle_task` 固化为同步模板方法（内部 `asyncio.run` 跑子类的
  `async process()`），完成态写 `task.artifacts`、追问/失败写 `task.status.message`；
  Agent 间调用改用官方 `A2AClient.send_task_async`。
- 教训：**用第三方框架前先读它的调用点源码**（谁调用我、传什么、期望返回什么），
  不能凭方法名想象契约；能用官方客户端就不要手搓协议。

**3. 配置字段错位（config.database.name 不存在）**
- 现象：MCP 数据层全部访问 `config.database.name`，而配置类字段叫 `database`。
  服务一启动就 AttributeError。
- 修法：把字段统一重命名为 `name`（读法 `config.database.name` 更自然），连接参数
  收敛到 `mysql_params` 属性。
- 教训：配置是"另一种接口"，同样需要联调；dataclass 字段改名要全局 grep。

**4. SQL 注入敞口**
- 现象：LLM 直出 SQL 原样 `cursor.execute(sql)`；结构化工具用 f-string 拼接
  （`WHERE city = '{city}'`）；订单查询同样拼接。
- 修法：新增 `sql_guard`（见第五节），LLM SQL 唯一入口 `execute_select` 强制校验；
  所有结构化 SQL 参数化；表名只能来自白名单映射。
- 教训：**"SQL 是模型生成的"不改变它是不可信输入的本质**；安全要做在执行点
  （MCP 服务端），而不是生成点（prompt）。

**5. 不诚实的 mock 与硬依赖**
- 现象：README 宣称接入和风天气/Aviationstack/Ticketmaster 三个真实 API，实际
  一行调用都没有，配置项是死代码；数据全是 random 生成；同时又硬依赖 MySQL，
  导致"假数据 + 真依赖"，demo 反而跑不起来。
- 修法：删除三个 API 的死配置；`MOCK_DATA=true` 显式入配置并在启动横幅声明；
  数据层加 SQLite 后端（默认），MySQL 变为可选；README 改为诚实版本。
- 教训：**demo 项目的第一要务是"能在干净机器上一条命令跑通"**；mock 不丢人，
  假装接了真实 API 才丢人。依赖能降级就降级（SQLite 回退是标准手法）。

**6. 工程化收尾**
- `.gitinore` 拼写错误导致 `.env`、`__pycache__` 全部被跟踪 → 更名 `.gitignore`，
  `.env` 转为 `.env.example` 模板。
- requirements.txt 迁移为 `pyproject.toml + uv.lock`（uv 管理，锁定可复现）。
- 新增两个可验证入口：`demo_offline`（数据层+防线+订单闭环）与
  `demo_a2a_e2e`（注入假 LLM，真实跑通 A2A 服务端/客户端 + MCP + SQLite）。
- 集成测试用 `RUN_INTEGRATION=1` 门控，保证 `pytest` 默认离线全绿。
